# ADR 0018：网关↔插件鉴权通道（WP-06.4 前置）

- 状态：已决定，实现中（网关侧客户端＋插件侧端点；第一个消费者是扩展表答案导出）
- 日期：2026-09-24
- 关联：WP-06 切片 06.3／06.4（扩展表答案、附件打包）；需求 R06-03、R06-04
- 前置 ADR：0003（引擎实例派生密钥与事件信封）、0006（C 档题型副表）、0009（发布网关）、
  0013（答卷读取与作答按页补取）、0014（组织免登，飞书回调的统一拒绝教训）、0016（访问规则的 `policyStatus` 回读端点）
- 契约：[`platform/contracts/plugin-channel-v1.md`](../../contracts/plugin-channel-v1.md)
- 读端契约：[`platform/contracts/question-extension-tables-v1.md`](../../contracts/question-extension-tables-v1.md)

## 背景：一条不存在的读取通道

WP-06.3 做完 SPSS SAV 导出之后停下了。「扩展表答案导出」与「附件打包」卡在同一件事上——
**插件副表里的作答，没有任何生产读路径**。

| 事实 | 位置 | 后果 |
|---|---|---|
| 副表读取方法 `fetchRows()` / `fetchState()` | `plugins/MjyQuestionExtensions/MjyStructuredAnswerStore.php:246/298` | 除 store 内部一处自调用外**只有测试在调**；C 档题型的作答写进去就再也出不来 |
| 发布网关只会说 RemoteControl | `platform/tools/publish-gateway/pubgw/rpc.py` | 纯标准库，没有数据库驱动，够不到副表 |
| RemoteControl 只派发一个插件事件 `remoteControlLogin` | `application/helpers/remotecontrol/remotecontrol_handle.php`（约 3971 行，全文仅此一处 `PluginEvent`） | **加不了插件 RPC 方法**——不改引擎核心就没有第二条路 |
| 平台的作答按页补取走 `export_responses` | ADR 0013 决定 7，`pubgw/responses.py` | 只能读引擎原生答卷表 `responses_<sid>`，副表不在其中 |

ADR 0016 的 `MjyRuntimePolicy::newDirectRequest`（`policyStatus`）证明了形状可行：
`GET index.php/plugins/direct?plugin=…&function=…`，插件自己出 JSON。但它**是匿名可达的**——
所以它只回份数、能否解析与摘要，密码哈希不出引擎。

**扩展表答案是个人数据。** 同样的形状不能照抄：一个匿名可读的答案端点，等于把整库作答挂在公网上。
因此这里要开一条新的信任边界——网关↔插件——并给它自己的鉴权。

## 可选方案

| 方案 | 做法 | 否决 / 采纳理由 |
|---|---|---|
| A. 改 RemoteControl | 在 `remotecontrol_handle.php` 里加派发点，让插件注册 RPC 方法 | **否决**。改引擎核心；许可分析结论 7 要求插件按衍生作品处理、核心改动最小化；且 RemoteControl 的会话口令是管理员全权口令，用它读答案等于没有最小权限。 |
| B. 网关直连引擎库 | 给网关配一份数据库账号 | **否决**。网关是纯标准库、无数据库驱动（ADR 0009）；私有化部署要额外开放客户机房数据库端口；且绕开插件意味着副表语义（结构版本、代次）要在网关重新实现一遍。 |
| C. 事件携带副表作答 | 桥接插件把副表行随事件推给平台 | **否决**。与 ADR 0013 否决方案 A 同因：`response.saved` 每页保存都触发，重复 PII 流经只追加的收件箱。 |
| D. **仿 `policyStatus` 的 `newDirectRequest` 端点 ＋ 共享密钥鉴权（采纳）** | 插件开一个签名保护的 `direct` 端点，网关用每实例派生的通道密钥验签调用 | 不改引擎核心；口令与密钥都不下放；副表语义留在插件里；按页读取，内存有界。代价是新开一条信任边界，本 ADR 余下部分就是这条边界的规格。 |

## 决定

### 1. 端点走 `newDirectRequest` 的 **GET**，不改引擎核心

`POST` 到 `plugins/direct` **到不了插件**：`application/config/internal.php:153` 的
`noCsrfValidationRoutes` 只豁免 `rest`、`admin/remotecontrol`、`plugins/unsecure`，
`plugins/direct` 的 POST 会先被 Yii 的 CSRF 校验挡下，`PluginsController::actionDirect()`
根本不会派发事件。`GET` 不受 CSRF 校验，因此参数走查询串。

- 刻意**不用** `plugins/unsecure`（`newUnsecureRequest`，CSRF 豁免、可 POST）：它与 `direct`
  一样是匿名可达的，换路由并不带来任何鉴权，却让本端点脱离 `policyStatus` 已经验证过的那条路。
- 代价：`sid`、`generation`、答卷号区间、分页游标会进 Web 服务器 access log。这些是**元数据不是作答值**；
  **答案值只出现在响应体里，永不进 URL**（决定 7）。这个代价是明账，记在「已知限制」。

### 2. 通道密钥：从既有实例密钥再派生一层，引擎侧零新增配置

```
实例密钥   = hex(HMAC-SHA256(平台主密钥,  "mjy-engine-events/v1/" + engineInstanceId))   // ADR 0003，已存在
通道密钥   = hex(HMAC-SHA256(实例密钥的 ASCII 字节, "mjy-plugin-channel/v1/" + engineInstanceId))
```

- 实例密钥就是引擎已经配好的 `MJY_PLATFORM_EVENTS_SECRET`（`MjyPlatformBridge.php:25`）。
  **插件自己派生通道密钥，引擎侧不需要任何新的环境变量。**
- 网关侧按引擎配置一份通道密钥（`PUBGW_ENGINE_CHANNEL_SECRET__<instance>`），由平台／运营用
  同一个公式算出后下发。
- **单向性是重点**：通道密钥是实例密钥的 HMAC 原像之外的值，拿到通道密钥推不出实例密钥。
  因此**网关被攻破，攻击者读得到副表答案，但伪造不了引擎事件**（伪造事件会污染平台的答卷投影，
  是更严重的完整性问题）。反过来也成立：这是最小权限，不是形式主义。
- PHP 的 `hash_hmac` 以字符串作密钥，所以 HMAC 的密钥字节就是那 64 个十六进制字符的 **ASCII 字节**，
  不是解码后的 32 字节——与 ADR 0003 `EngineEventKeys.signingKey()` 的注意事项完全相同，两端必须一致。
- 派生前缀带版本号 `v1`：将来换算法时升版本，新旧密钥互不相同，不会出现「换了算法但旧签名还能过」。

### 3. 轮换：插件同时接受当前与上一代密钥，网关只用当前

引擎新增一个**可选**环境变量 `MJY_PLATFORM_EVENTS_SECRET_PREVIOUS`。插件从「当前」和
（若存在）「上一代」各派生一个通道密钥，验签时逐个做**定时安全比较**，任一通过即放行。

轮换步骤（无停机）：

1. 平台轮换主密钥或单实例密钥，算出新的实例密钥与新的通道密钥；
2. 引擎设 `MJY_PLATFORM_EVENTS_SECRET_PREVIOUS=<旧实例密钥>`，`MJY_PLATFORM_EVENTS_SECRET=<新实例密钥>`，重载；
3. 网关改配新的通道密钥；
4. 确认流量正常后，删掉 `MJY_PLATFORM_EVENTS_SECRET_PREVIOUS`，重载。

**最多两个密钥同时有效**，没有「一直堆积」的余地。上一代密钥没有独立的到期时刻——第 4 步就是到期，
运维步骤里写死。密钥缺失或不足 32 字节时**不派生任何密钥**，端点拒收一切（失败即关闭，同 ADR 0003）。

### 4. 验签覆盖整个规范化请求，不只是请求体

```
签名串   = "<timestamp>" + "." + <规范化查询串>
X-Mjy-Channel-Signature = hex(HMAC-SHA256(通道密钥的 ASCII 字节, 签名串))
```

规范化查询串 = 除 `sig` 外的**全部**查询参数，按参数名升序（同名参数按值升序），
各自 RFC 3986 百分号编码后以 `k=v` 用 `&` 连接。

为什么覆盖整个查询串而不是只覆盖某几个参数：

- 它**包含 `plugin` 与 `function`**，所以一个签好的请求无法被改投到别的插件或别的插件函数；
- 它**包含 `sid`、`generation`、答卷号**，所以截获到一个合法请求的人无法把它改成「读别人的答卷」。
  只签请求体（本端点是 GET，没有体）或只签部分参数，都会留下这个改投缺口。
- 未列入白名单的参数一旦出现即拒绝（决定 6），因此攻击者也不能靠**追加**一个不在签名里的参数来改变行为。

时间戳是 Unix 秒，偏差超过 **±300 秒**即拒绝——与 `pubgw/auth.py:MAX_SKEW_SECONDS` 和
`response-read-v1.md` 的既有约定一致，两端不引入第三个数字。

**防重放。** 本端点是只读且幂等的：重放一个合法请求，重放者拿到的是他本就已经拿到过的那一页数据，
不产生新的信息泄露，也不改变任何状态。因此不引入一次性随机数存储（它需要每请求一次数据库写入，
把只读端点变成写端点，代价大于收益）。真正需要挡住的是**改投**与**长期有效**，分别由
「签名覆盖整个查询串」与「±300 秒窗口」解决。传输层强制 HTTPS，窗口内的重放需要攻击者已经在 TLS 之内。

### 5. 分界线画在验签这一步：验签**之前**的拒绝全部统一，验签**之后**的拒绝才可区分

这是本 ADR 最要紧的一条，分界线的位置必须说清楚，不能含糊成「一律统一」或「一律分类」。

**验签通过之前（含验签本身）的一切拒绝，返回同一个状态与同一段响应体：**

```
HTTP 401
Content-Type: application/json; charset=utf-8
Cache-Control: no-store
{"error":"unauthorized"}
```

覆盖：签名头缺失、时间戳格式不对、时间戳过期、签名格式不对、签名不匹配、通道密钥未配置、
`target`/`function` 之外的参数白名单不符、参数形状或个数越界、`sid` 不是数字。
**不做任何区分，原因只进服务端日志**（`Yii::log`，类别 `plugin.MjyQuestionExtensions`），带稳定原因码。

这一条是 ADR 0014 那次修复的直接继承：飞书事件回调曾因「未签名请求跳过验签却仍用调用方给的 IV 解密，
且各种失败返回不同状态与消息」而成为 CBC 填充预言机，匿名方不知密钥即可逐字节解密并伪造事件
（见 `platform/docs/p2/progress.md:80`）。**任何按失败原因分叉的应答都是预言机。**

**验签通过之后的拒绝可以带明确错误码**（`400` / `404` / `409`），理由是：
签名覆盖整个查询串（决定 4），**不持有通道密钥的人根本走不到这一步**，
因此这里的区分只有我们自己的网关看得见，构不成任何预言机。
反过来，若把「体量超限」也压成 401，我们自己的客户端就再也分不清「密钥配错了」和「这一页太大」——
那是把可诊断性白白丢掉换一个并不存在的安全收益。

具体地，`sid` 不存在 / 代次不匹配 **不返回 404 也不返回错误**，而是返回 `200` 加空结果：
它们在正常运行中就会发生（问卷刚停用再激活、平台的代次判定慢一拍，见 ADR 0013 决定 3），
是**正常的空**，不是错误。这样也顺带让「问卷是否存在」不出现在应答里。

与 `pubgw/auth.py` 的差别是**刻意的**：平台→网关那条边界的 401 带 `reason`，因为两端都是服务端、
没有匿名可达面，可诊断性优先。本端点任何人都能 GET，所以验签之前必须统一。
两处不一致的地方就在这里写明，避免后来者「顺手统一」成错的那一边。

### 6. 顺序：先验签，再限流，再一切；未验签的请求零数据库、零解密

```
1. 方法与 target/function 匹配           （不匹配 → 静默 return，让别的插件处理）
2. 参数白名单与形状检查                   （纯字符串操作，无 IO）
3. 派生通道密钥（读环境变量，进程内 HMAC）
4. 验签 ＋ 时间戳窗口                     ← 这条线以上不碰数据库、不碰任何作答
─────────────────────────────────────────
5. 限流
6. 查 sid / 代次，读副表，出 JSON
```

**这里刻意与 `AnonymousRateLimitFilter` 的顺序相反**，理由要写明白，否则后来者会以为是疏漏：

- 飞书回调那条链把限流放在验签**之前**，因为验签要先做 AES 解密，成本高，洪水打得动。
- 本端点的验签是**纯进程内的一次 HMAC**，密钥从环境变量派生，不读数据库、不读插件设置表。
  未签名洪水的单请求成本因此就是一次哈希。
- 反过来，若把限流放在验签之前，就必须为匿名请求维护计数器——PHP 没有常驻进程，
  桶只能落库（或落 Yii 缓存，在多节点部署下同样是外部存储）。那等于**让未验签的请求触发数据库写入**，
  亲手造出本来不存在的放大面。

### 7. 限流：两层，都在验签之后

| 层 | 限的是什么 | 手段 | 拒绝形式 |
|---|---|---|---|
| 请求形状 | 一次调用最多点名多少 | 答卷号 ≤ 200 个／次，题目代码 ≤ 50 个／次 | 验签**前**判定（纯字符串），统一 401 |
| 结果体量 | 一次调用最多取回多少 | 单元格 ≤ 20000 个／次（按 `LIMIT 20001` 探出溢出，不静默截断） | 验签**后**判定，`400 {"error":"page_too_large"}` |
| 速率 | 已验签调用方的调用频次 | 按 `(engine_instance_id, survey_id)` 的固定窗口计数，落在插件自己的表里 | `429`，响应体不说原因 |

结果体量**绝不静默截断**：截断会让导出少几行而没有任何人察觉，比报错危险得多。

429 是统一拒绝的唯一例外，且**不构成预言机**：它只取决于速率，不取决于请求内容——
与 `AnonymousRateLimitFilter` 的 429 同理（同文件类注释：「429 的响应体不说明原因，和统一 401 一样不泄露…」）。
限流只可能被已经持有通道密钥的调用方触发，作用是给「我们自己的网关跑飞了」和「密钥泄露后的批量拖库」封顶，
不是用来挡匿名洪水的（那由决定 6 的零 IO 负责）。

### 8. 日志绝不记答案值，也绝不记密钥

允许记：`engineInstanceId`、`surveyId`、`generation`、答卷号**区间**、题目代码、返回行数、判定与原因码、耗时。

**禁止记**：任何 `cell_value`、`errors` 列的内容、通道密钥、实例密钥、签名值、完整查询串（它含 `sig`）。

网关侧同样约束，沿用 `pubgw/responses.py` 已有的自律（其模块注释：「作答是个人数据：本模块的日志
只记实例、sid、条数与失败的 RPC 方法名，从不记值或引擎错误原文」）。

### 9. 第一个消费者：扩展表答案进入按页作答读取，但**单列一段**，不并进扁平字段

平台不直接与插件通信——**信任边界只在网关↔插件之间**，平台仍然只对网关说
`POST /v1/responses/read`（ADR 0013 决定 7、契约 `response-read-v1.md`）。
网关在应答那次调用时，除既有的 `export_responses` 之外，**对同一页答卷号**再走一次本通道。

**哪些题要走通道，网关已经知道，不需要额外的发现调用。** 发布时每道 C 档题的
`QuestionBinding.side_table`（`pubgw/fieldmap.py:53`，由 `questions/themes.py:234` 产出，
`binding.py:81` 读回）已经带着 `cellTable` / `structureVersion` / `columns` 存进了绑定记录。
网关按绑定挑出有副表的题目代码，作为本通道请求的 `questionCodes`。

**应答里单列一段，不并进 `answers` 的扁平字段。** 现有的作答模型是
`答卷号 → {引擎列名: 值}`（`responses.py:145` `read_answers`），是一维的；副表作答是
**行 × 列**的二维数据，且**行数逐份答卷不同**。把它压进扁平列需要一个「最多多少行」的约定，
而那个上限在读取时并不知道（字段字典是发布时冻结的，副表行数是作答时才产生的）。
硬压的结果要么截断作答，要么让列集随数据漂移——两者都不可接受。

因此读取应答新增一段并列的 `extensionAnswers`：

```
答卷号 → 题目代码 → { structureVersion, isValid, rows: [ {列代码: 值}, … ] }
```

`answers` 一段的形状与语义**完全不变**，`response-read-v1` 不破坏兼容；平台侧按需消费新的一段。
怎么把二维数据铺进导出的一维表头（按批次内最大行数展开，还是另出一张附表），
是导出车道的决定，不在本 ADR。

两个来源都**失败关闭**：任一不可达即整页 503 `answers_unavailable`，绝不返回
「看着完整、其实缺了扩展题」的一页（ADR 0013 决定 8 的同一条规矩）。

副表按 `(实例, sid, 代次, 答卷号, 题目代码)` 取值。代次与 ADR 0013 决定 3
「只为最近代次补取作答」的判定保持一致——**代次不匹配时返回空，绝不返回别的代次的数据**。

### 10. 端点为副表补一个按页批量读，`fetchRows` / `fetchState` 保持单答卷语义

既有的 `fetchRows()` / `fetchState()` 是「一条答卷的一道题」的访问器。按它们实现分页读会是
N+1：200 条答卷 × 若干扩展题 = 数百次查询。因此 store 增加一个批量读方法，一次查询取回
整页的单元格，端点按 `(答卷号, 题目代码, 行序号)` 归拢。单答卷访问器**保留不动**，
仍是校验与投影路径的接口。

## 已知限制

1. **查询串进 access log**（决定 1）。`sid`、代次、答卷号区间会留在 Web 服务器日志里。
   答案值不会。要消除这一条，得让 `plugins/direct` 支持 POST，那是引擎核心改动，不在本车道。
2. **签名里没有一次性随机数**（决定 4）。±300 秒窗口内、TLS 之内的重放读得到同一页数据。
   只读幂等端点上这是可接受的；本通道**不得**用来承载任何有副作用的操作——
   将来若要加写操作，必须先补随机数存储，并重开本决定。
3. **上一代密钥没有独立到期**（决定 3）。靠运维步骤第 4 步删除。忘记删除等于把轮换窗口无限延长；
   可观测性缺口：目前没有「本次验签用的是上一代密钥」的指标。后续补一条日志计数。
4. **限流是固定窗口不是令牌桶**（决定 7）。窗口边界处可能放过接近两倍的额度。
   对「给已验签调用方封顶」这个目的够用；`AnonymousRateLimitFilter` 用令牌桶是因为它挡的是匿名洪水。
5. **导出的表头展开不在本 ADR**（决定 9）。网关把二维副表作答交到平台手里就算到位；
   平台侧怎么把它铺进 CSV／XLSX／SAV 的一维表头（按批次最大行数展开，还是另出一张附表），
   由导出车道按 ADR 0015 决定 6 的「字典驱动列」重新决定。在那之前，
   `extensionAnswers` 这一段有数据但还没有消费者。
6. **附件打包不在本车道**。它还要解决 `get_uploaded_files` 把整份答卷的文件 base64 进一个 JSON
   应答的内存问题，与本通道正交，另开切片。
