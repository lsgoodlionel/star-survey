# ADR 0019：平台层级字典与多级下拉的版本绑定

- 状态：已实现，单元／集成与**真引擎端到端**均通过（平台 1083→1132，网关 941→967，
  插件 PHPUnit 双库 110→147，`run-question-themes.sh` 双库各 248→278 项）
- 日期：2026-09-24
- 关联：[ADR 0006](0006-question-types.md)（三档承载方式）、[ADR 0012](0012-republish-and-drift.md)（新版本即新引擎问卷）、
  [ADR 0016](0016-access-policy.md)（发布时物化 `participants`、平台重算摘要）、[ADR 0018](0018-gateway-plugin-channel.md)（网关↔插件通道）；
  契约 [question-extension-tables-v1](../../contracts/question-extension-tables-v1.md)、
  [platform-dictionary-v1](../../contracts/platform-dictionary-v1.md)
- 需求：R02-03 多级下拉（省／市／区三级联动）；下游还有 R02-34 门店字典、R02-35 城市分级

## 背景

R02-03 要的是「省 → 市 → 区」这种逐级收窄的选择。引擎的单选题可以放选项，但：

| 路子 | 为什么不行 |
|---|---|
| 把三千多个节点塞进题目属性的枚举取值 | 枚举列的取值上限是 200（`MAX_COLUMN_OPTIONS`）。提高上限也不解决问题：每道题重复一份、每次发布重传一份，而且作答页要一次全下发 |
| 三道独立的单选题＋逻辑 DSL 过滤 | 「市」的选项集合依赖「省」的作答，过滤规则要写三千条 |
| 让浏览器端联动，服务端不管 | 作答者可以关掉 JavaScript 直接写 JSON，也可以改 DOM 把广州塞到北京下面 |

所以这条需求卡的不是题型，是**平台缺一个层级字典服务**。WP-02 的映射表把它记成「R02-03 需平台字典服务」，
本 ADR 就是那个服务，以及它与已发布问卷之间的绑定方式。

字典不止行政区划：门店（R02-34）、城市分级（R02-35）、品类树都是同一形状，所以设计里没有任何行政区划专有的假设。

## 决定

### 1. 字典是**平台控制平面资产**，不是租户数据

三张表（`platform_dictionary`、`platform_dictionary_version`、`platform_dictionary_node`，V900）
与 `platform_survey_template` 同一口径：**故意不做行级安全**。一本行政区划要对所有租户可见，
而行级安全的前提恰恰是「只看得见自己租户的行」。可见性改由查询条件承担——
租户侧只查已发布的版本，写入只走 `/v1/platform/**`（`PlatformWebConfig` 的拦截器要求 `platform_operator`）。

表里没有任何租户数据：字典是参考数据，不是谁的答卷。

节点代码在**一版之内全局唯一**（行政区划的 GB/T 2260 本来就是这样）。这条选择让一条作答只存代码就够，
路径判定一次 `IN (…)` 拿齐全部层级，不必逐级往返。

### 2. 版本与已发布问卷的绑定：**发布那一刻固化进定义快照**

这是本 ADR 的核心问题。字典会更新（区县撤并、改名），而已发布问卷引用的必须是确定的那一版，
否则半年前那份答卷里的「XX 区」会在今天的字典里变成非法路径。

做法与 ADR 0016 的 `participants` 物化**逐条对应**：

| 阶段 | 发生什么 |
|---|---|
| 草稿 | 作者只写**引用哪本字典**（`themeOptions.dictionary`）。写了 `dictionaryVersion` / `dictionaryDigest` / 顶层 `dictionaries` 一律被 `SurveyDefinitions.normalize` 摘掉 |
| 发布（`freshAttempt`） | `SurveyDictionarySource.pin()` 把每本被引用的字典固化成**当前版本**，把版本与内容摘要写回每道题，并在定义顶层放一份紧凑三元组的节点快照 |
| 之后 | 定义快照不可变（`survey_publish_attempt.definition`、`survey_published_version`），所以这一版从此跟着这一版问卷走 |
| 字典更新 | 运营发布新的一版，`platform_dictionary.current_version` 跟着走。**已发布的问卷一个字都没变** |
| 改版再发布 | ADR 0012 的重新发布＝新的引擎问卷，那时才重新固化到新的当前版本 |

**为什么固化的是"当前版本"而不是让作者选**：作者选版本意味着作者要跟踪字典的发版；
而"发布时用当下最新的那一版、之后永不改变"是唯一一条不需要任何人记着去做的规则。
需要钉死某个历史版本的场景（合规回溯）目前没有，留作后续（见"缺口"）。

**为什么快照要随定义走、而不是让引擎回查平台**：引擎上没有平台连接（ADR 0003 起就是单向的）。
插件要在服务端判定路径，引擎里就必须有这一版字典。

### 3. 快照的运输：走 `.lss` 的 `plugin_settings`，落地成引擎侧的索引表

网关把定义顶层的 `dictionaries[]` 编成 `lime_plugin_settings` 的一行
（`name=MjyQuestionExtensions`，`key=dictionaries`，model=Survey）。这条通道是现成的——
访问策略（ADR 0016）已经这么走，**不新开信任边界**。`value` 列是 `mediumtext`（16 MB），
三千多个节点的紧凑三元组约 120 KB，装得下。

**运输方式不是查询方式**：插件首次用到时把它物化进两张带索引的表
（`mjyquestionextensions_dict_version` / `_dict_node`），之后判定路径与翻页全是索引查询。
物化**按摘要幂等**：装过的同一摘要什么都不做，摘要不一致说明是另一份数据，整版换掉——
与旧节点混在一起会让"跨版本的节点"这类篡改变成合法路径。

因此代价是有边界的：一本字典一版在一台引擎上只物化一次，与有多少份问卷、多少份答卷无关。
节点数上限 8000（`DictionaryLimits.MAX_NODES`），由平台定义快照的 1 MiB 上限倒推而来。

### 4. 作答页一次只取一层

树有数千节点，作答页不能一次全下发。主题的脚本向插件的 `dictionaryNodes` 端点按页取，
选了上一级才去取下一级（`MjyDictionaryNodesEndpoint`，`GET index.php/plugins/direct`）。

这条端点**没有签名**——作答者手里没有通道密钥，也不该有。它与 ADR 0018 那条网关通道是两回事，
两条规矩刻意不照搬：

- **不统一成一个 401**。那条规矩是为了不给持密钥的攻击者留预言机；这里读的是公共参考数据，
  区分"参数写错了"与"这份问卷没用这本字典"不泄漏任何东西，含糊其辞只会让前端没法自查。
- **不接 `MjyChannelRateLimit`**。那张计数表是落库的，它自己的注释写得很清楚：
  放在验签之前就等于为匿名请求维护一张表、亲手造出放大面（ADR 0018 决定 6）。
  这条端点本来就没有验签，接上去只会把那个放大面造出来。

取而代之的自律是：**形状检查全部在任何数据库访问之前**（参数不合法的请求一次查询都不会发生），
合法请求是两次带索引的查询。授权是"这份问卷真的有一道题引用了这本字典的这一版"，
所以它给不出任何已发布问卷没有向作答者展示过的东西。
**已知缺口：这条端点没有按 IP 的限流**（见"缺口"）。

### 5. 服务端校验：整条路径，不是逐个单元格

多级下拉走副表（ADR 0006 的 C 档），整题一行、一级一列，列的类型是新的 `dict`——
取值集合由 (字典, 版本, 层) 决定，不在列定义里。

**判定必须看整条路径**。"440100 是不是一个合法的市"单看一格是成立的，但"它在北京下面"不成立。
`MjyRepeatingTableValidator::checkDictionaryPaths()` 把同一本字典的几个 `dict` 列按 `level` 排好，
逐级核对三件事：这一级的代码在**这一版**里、它的层深正好是这一级、它的父节点**恰好**是上一级。

**查不到就拒**（失败关闭）：引擎上没装这一版、或者根本没有字典可用时，这道题谁也交不了。
那正是应有的结果——发布期的对账（网关 `E_DICTIONARY_MISSING`）本就不该让这种问卷发得出去。

### 6. 字典版本进结构摘要，但走的是一条不改变既有摘要的路

副表的 `structureDigest` 回答"这些单元格还能不能按这一版列定义读回来"。字典换了一版，
单元格里那些代码的含义就变了，与改了枚举选项是同一回事，所以它必须进摘要。

实现上在原有八个字段**之后**追加 `|<字典>@<版本>`，且只在字典列上出现，
因此既有八个题型的摘要**逐字节不变**（`sd1:` 的金标准不用动）。

### 7. 摘要不在网关重算

平台的 `dg1` 覆盖的是平台侧节点的规范形式；网关拿到的是紧凑三元组。两边各算一遍等于再造一份
规范化规则，分歧会**误挡正常发布**——ADR 0016 决定 5 已经为此付过一次代价（两份 `policyDigest`
实现靠一张共用向量表才勉强钉住）。所以网关只做对账（题目引用的摘要 vs 快照声明的摘要），
真正的核对在引擎侧：插件按 (字典, 版本, 摘要) 判断装着的那份是不是同一份。

## 数据从哪来

**仓库不附带任何行政区划数据集**，与 ADR 0016 对 GeoIP 的口径一致：这类数据集各有各的许可与署名义务
（国家统计局的统计用区划代码、民政部的行政区划代码、各家整理的开源数据各不相同），
选哪一份、如何署名应当由交付方按许可决定，不由本仓库替他们决定。

导入路径是**运维通过运营端点导入**：

```
POST /v1/platform/dictionaries                              建字典（代码、名称、最深几层）
POST /v1/platform/dictionaries/{code}/versions              建草稿版本
POST /v1/platform/dictionaries/{code}/versions/{v}/nodes    整棵树一次灌进来
POST /v1/platform/dictionaries/{code}/versions/{v}/publish  发布：算摘要、冻结、设成当前版本
```

整棵树一次灌进来而不是增量追加：叶子标记与深度都要看全树才算得出来，分批导入意味着每一批都要
重算全树，还要处理"批与批之间这一版是什么形状"。节点数有硬上限，一次一棵树是更简单也更可解释的选择。

树的形状（孤儿、环、超深、重复代码）在**导入时**就判，不拖到发布——让人灌完几千个节点再说
"其中一个是孤儿"是白费一次。发布时会再推一遍作为最后一道闸门。

### 数据更新的迁移路径

1. 运营建**新的一版**（`2025.1`），灌入新数据，发布。旧版 `2024.1` 原样留着，**永不删除**；
2. `platform_dictionary.current_version` 指向新版，此后**新发布**的问卷固化到新版；
3. 已发布的问卷仍按 `2024.1` 判定——它们的定义快照里写着 `2024.1`，引擎上也装着 `2024.1`；
4. 想让某份在线问卷用上新字典，就改稿重新发布（ADR 0012），那是一份新的引擎问卷、一批新的答卷；
5. 两版的节点在引擎侧按 (字典, 版本) 分开存放，互不可见——所以「拿上一版的节点填这一版的题」
   会被当成不存在的代码拒掉。

引擎侧的旧版快照目前**不会被清理**（见"缺口"）。

| 平台单元／集成 | `cn.mjy.platform.dictionary` 四个测试类 | 49 个新用例（生命周期 13、读取与篡改 21、发布固化 7、HTTP 8），全套 1083 → 1132 |
| 网关单元 | `tests/test_question_cascading.py` | 26 个新用例，全套 941 → 967 |
| 插件 PHPUnit | `MjyDictionaryStoreTest`(13) / `MjyDictionaryPathTest`(13) / `MjyDictionaryNodesEndpointTest`(11) | 37 个新用例，全套 110 → 147（337 断言），MariaDB 与 PostgreSQL 双库 |
| 真引擎端到端 | `platform/deploy/test/run-question-themes.sh` | 双库各 248 → 278 项。两道多级下拉题分别引用**同一本字典的两版**，证明两版在引擎上共存且互不串味 |

篡改用例在两层各覆盖一遍：

- 插件层（`MjyDictionaryPathTest`）：跨省的市、不存在的区、跨版本的节点、跳级、不从根开始、
  缺一级、没有字典可用、引擎上没装这一版。把 `checkDictionaryPaths()` 整段拿掉做变异验证，其中 7 条转红。
- 真引擎层（场景 D）：同样七条走真实 HTTP 提交，每条都断言两件事——**被拒且作答者留在本页**、
  **这一轮会话没有留下任何已提交答卷**。跨版本那条用的是只存在于 `2023.1` 的 `440104`，
  而那道题钉在 `2024.1` 上。

**真引擎端到端抓到一处只有它能抓到的缺陷**：`DbStorage::getGeneric()` 已经替调用方
`json_decode` 过 `plugin_settings` 的值（`Storage/DbStorage.php:60`），而插件原先只认字符串，
于是字典一本都装不上、每条合法路径都被判成非法。单元测试全绿，e2e 第一次跑就红。

## 缺口

- ⏳ 作答页脚本的**交互**没有浏览器里的测试。端到端证明了标记与 JS 真的出现在页面上、
  服务端对手写信封的判定正确，但"点了省之后真的取到了市"这一步只有 `dictionaryNodes`
  端点自己的 PHPUnit 覆盖，没有在真浏览器里点过（与前几波三套新主题同一口径）。
- ⏳ 作答页的字典端点**没有按 IP 的限流**。它是只读的公共参考数据、两次带索引的查询，
  比作答页本身轻，但仍是一个匿名可达的端点。引擎的 `AnonymousRateLimitFilter` 不覆盖 `plugins/direct`。
- ⏳ 引擎侧的旧版快照不会被清理。问卷收口（ADR 0012 决定 3）之后那一版字典可能再没人引用，
  但没有任何东西去回收它。一本字典一版约 120 KB，积累速度很慢，但没有保留期策略。
- ⏳ 作者不能钉死某个历史版本：固化的永远是发布那一刻的当前版本。合规回溯场景需要时再加。
- ⏳ 节点数上限 8000，由定义快照的 1 MiB 倒推。全国行政区划到区县约 3200 个节点够用，
  到**乡镇街道**（约 4 万）不够。真要到那一级，快照就不能再随定义走，需要一条专门的安装通道
  （`plugins/unsecure` 的 POST 是 CSRF 豁免的，可以承载，但那是新的信任边界，要重开 ADR 0018 决定 4）。
- ⏳ 搜索是 `LIKE '%…%'`，走不了索引。一版字典的节点数有硬上限，最坏情况是扫一版，
  在可接受范围；真要做前缀以外的高效搜索需要全文索引。
- ⏳ 一道题只能引用一本字典的一条路径链。同时问户籍地与现居地要两道题
  （列定义支持多组，校验也支持，但主题脚本只渲染一组）。
