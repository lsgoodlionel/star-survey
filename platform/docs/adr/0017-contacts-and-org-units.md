# ADR 0017：三类身份、通讯录导入与部门权限（WP-18 切片 18.1 / 18.2）

- 状态：已实现（平台侧；发布时物化参与者见决定 8，投放与组织同步接入见"缺口"）
- 日期：2026-09-23
- 关联：WP-18 切片 18.1（三类身份分离与导入去重）、18.2（组织/标签/部门权限）；
  需求 R18-01（导入与错误行反馈、离职停权）、R18-02（部门树、部门管理员范围、标签隔离）、
  R18-04（来源保留、去重、可撤回）、R18-08（openid 作用域不混淆）部分；
  R18-03 只做到"把人映射到参与者令牌"，发放与投放属于 delivery 车道
- 前置：ADR 0014（组织免登与 identity_binding）、0011（资源树与授权）、0015（导出作业的断点模型）、
  0016（访问策略与邀请码 / 引擎 `tokens_<sid>`）
- 代码：`cn.mjy.platform.contacts`；迁移 V800–V804

## 背景

蓝图 §7.9 要求"统一 Principal 只作身份关联，三种业务实体独立权限和生命周期"，
验收"不同应用同 openid 不合并""离职后立即失权"。仓库里已有的相关能力：

| 已有 | 位置 | 够不够 |
|---|---|---|
| 外部身份绑定按 (租户, provider, app_id, external_id) 唯一 | `identity_binding`（V103/V104） | 够，但只解决"登录主体"，没有通讯录 |
| 离职撤权 | `identity_binding_revocation`（V107/V110）＋ `MemberService.removeBySystem` | 够，缺"通讯录的数据范围也要跟着收回" |
| 成员与席位（STAFF 占位，PARTICIPANT 不占位） | `cn.mjy.platform.access`（V401） | 够，说明参与者不是平台员工 |
| 资源范围授权与继承 | `access_resource` / `access_grant` | 够，但它的树是"项目/文件夹/问卷"，不是部门 |
| 断点续跑的后台作业 | `ResponseExportWorker`（ADR 0015） | 直接照搬 |

缺的是：联系人本身、名单与导入、部门树与标签、部门级的数据范围。

## 决定

### 1. 三类身份各自成行，永不隐式合并；关联是显式的、留痕的、可撤销的

`contact.kind ∈ {staff, org_member, respondent}`：平台员工账号、组织成员（来自组织免登 / 通讯录同步）、
答卷联系人。同一个自然人可以同时是三者，就是三行。

**不合并的判据写在表上，不只写在代码里**：

- 名单内去重的唯一索引是 `(tenant_id, list_id, dedupe_value)`，而一份名单只装一类身份
  （`contact` 到 `contact_list` 的外键带 `kind`）。所以"员工名册里的李四"与"答卷受众里的李四"
  即使邮箱相同也分属两个去重域，永远是两行。
- 不属于任何名单的目录联系人按 `(tenant_id, kind, provider, app_id, external_id)` 唯一。
  **`app_id` 在键里**：同一串 openid 出现在两个应用下必然是两行（验收第一条）；
  这与 `identity_binding` 的键口径一致，两边不会一个合一个不合。

关联走 `contact_link`：无向、按 uuid 文本序规范化存储、同一对同时只有一条有效关联，
写入记审计、撤销写 `unlinked_at`（表上只授出这两列的 UPDATE，不能删、不能改事实）。
**关联不是合并**：两行各自保留 id、名单、部门、标签、状态与生命周期；
没有任何接口会把两行并成一行，也没有"主记录"的概念。

被拒绝的替代方案：写一个 unionid 合并器，或者让去重跨名单生效。前者要求平台替客户判断
"这两串 id 是同一个人"，在应用维度上根本不成立；后者会让一次营销导入悄悄改掉员工名册里的人。

### 2. 去重键按名单选定，建后不可改；比较的是规范化值

`contact_list.dedupe_key ∈ {email, phone, employee_id, external_id}`，建名单时由租户选定。
不做"租户级全局去重键"：HR 花名册按工号、营销名单按手机号是同时存在的正当需求。
建后不可改，因为改键等于重新划分已有行的去重分组——要换就新建名单再导入。

规范化：邮箱去空白转小写；手机号去掉空格、连字符、括号与点，保留可选的 `+`；
工号去空白、区分大小写；外部身份是 `provider|app_id|external_id` 三段拼接。
规范化结果存在 `contact.dedupe_value` 上，唯一索引落在它上面——**判重由数据库保证，不是靠应用自觉**。
手工建人与批量导入共用同一个 `ContactNormalizer`，两条路径的判重口径不会漂移。

### 3. 导入：逐行判定、坏行不终止、断点续跑

提交时只做结构解析（CSV 需表头；JSON 是同名键的对象数组），把每行存成一个 JSON 对象，
作业落库即返回 202。后台 `ContactImportWorker` 逐行推进，**一行一个事务**，事务里做三件事：
写联系人、写这一行的结果、把断点 `next_row` 推进一格。于是：

- 进程在任何时刻挂掉，未提交的那一行整体回滚，恢复后从同一行重来——不漏行；
- 结果行 `ON CONFLICT DO NOTHING`，只有真正插入了结果才给计数器加一，
  所以即使同一行被重放（崩在提交与推进之间的极端时序），也不会重复建人、不会重复计数。

每行四种结局（R18-01"错误行反馈准确"）：

| 结局 | 判据 | reason 例 |
|---|---|---|
| `created` | 按去重值在本名单里查不到 | — |
| `updated` | 查到了，且这一行不是本次作业刚写过的那个人 | — |
| `duplicate` | 查到的人**已被本次作业写过**（文件内重复） | `duplicate_in_file` |
| `invalid` | 规范化或校验不通过 | `missing_dedupe_key`、`invalid_email`、`invalid_phone`、`invalid_employee_id`、`invalid_external_id`、`unknown_org_unit`、`invalid_name` |

"文件内重复"用作业自己的结果表判定，不另存内存集合，因此断点续跑后判据仍然成立。
坏行只记一条结果，作业继续；整批只有在解析不出结构、超出行数/体积上限、
或者提交者本人已经失去通讯录权限时才整体失败。

租约、退避、`runOnce()` 按租户扫描的形状照搬 ADR 0015 的导出作业；
`platform.contacts.import.enabled=false` 时整个定时器不装配，测试直接驱动 worker。

### 4. 部门范围：收窄 `AccessDecisionService` 的判定，不另起一套权限

**不改 access 模块**（本切片对 `cn.mjy.platform.access` 零改动）。规则只有三条：

1. 租户级 `manage-settings` → 全租户联系人（租户通讯录管理员：`tenant_owner`、`org_admin`）；
2. 否则租户级 `manage-members` → 只看 `contact_scope_grant` 指定的部门**及其子孙**；
   一条范围行都没有就什么都看不到；
3. 两者都没有 → 拒绝，原因码原样取自 `AccessDecisionService`（如 `no_matching_grant`）。

"能不能碰通讯录"完全是 access 的判定；`contact_scope_grant` 只是一个**收窄**维度，
永远不能放宽：授予范围本身要求 `manage-settings`，所以部门管理员无法自己扩大范围。
范围行可设到期时间、可撤销、每次变更都写审计。

为什么不把部门塞进 `access_resource`：那棵树的语义是"项目/文件夹/问卷"，
`kind` 的 CHECK 与"项目才是根"的约束都是为它写的；塞进去要改 access 的迁移与列表接口，
而部门与项目的生命周期、命名空间、管理员都不是一回事。

为什么第 2 条是"没有范围行就什么都看不到"而不是"退回全租户"：
否则撤销一个部门管理员的最后一条范围行会把他**提权**成全租户管理员。失败即关闭。

范围过滤写在 SQL 里（一段递归 CTE 求出可见部门集合，再与查询条件求交），
不是先查出来再在内存里过滤——分页、计数与越权判定用的是同一份条件。
没有部门的联系人只有全租户管理员看得到。

部门树用触发器兜底防成环（照搬 V402 的 `access_resource_guard` 形状）；
移动部门要求**新旧父节点都在调用者范围内**，否则等于把人搬出/搬进别的部门。
移动之后可见性立刻按新位置计算，没有缓存，不会留下"看得见旧部门的人"的窗口。

### 5. 参与者令牌：平台只记映射，不发码也不发送

`contact_participation` 把"联系人 ↔ 某一版已发布问卷的参与者令牌"记下来：
`(contact_id, survey_id, version_no, engine_instance_id, engine_sid, participant_token)`。

- 令牌**不由平台生成**。网关 `add_participants` 总是让引擎生成 token，定义里写的会被替换，
  平台要发的邀请码只能在发布后拿到——现在随发布回执一并返回（契约 publish-gateway-v1
  「邀请码回读」），由发布收尾自动登记（决定 8），不再需要谁去查 `tokens_<sid>`。
- 一个联系人在某一版上同时只有一个有效令牌；同一 `(实例, sid)` 下一个令牌同时只属于一个联系人
  （ADR 0016"续答令牌不互用"）。两条都是部分唯一索引，撤销后名额与令牌一起释放。
- 按已发布版本记账：改版再发布是新 sid（ADR 0012），新旧版本各有各的映射，互不覆盖。
- **发送不在本模块**。`ContactParticipationService.current/forSurvey/revoke` 就是投放车道要调的接口。

### 6. 个人信息不进日志、不进审计资源串、不进错误体

联系人的姓名、邮箱、手机号、工号、外部 id 与参与者令牌都是敏感数据：

- 审计的 `resource` 只放 UUID 与动作码（`contact/<uuid>`、`survey/<uuid>/v2`），永不放字段值；
- 导入的逐行结果只有行号、结局、错误码与命中的联系人 id，**没有行内容**，可以直接展示给运营；
- worker 的日志只写作业 id、行号与结果码；作业的 `last_error` 只写错误码（表上限长 200）；
- 原始导入行（含个人信息）在作业完成时删除，只留不含个人信息的结果。

### 7. 隔离与最小授权

每张新表都是租户表：`tenant_id NOT NULL` ＋ 四行行级安全模板，所有访问包在 `TenantScope` 里，
跨表外键一律复合 `(tenant_id, …)`（外键检查绕过行级安全，见 V108 的做法）。
名单、部门、联系人、标签、导入作业与逐行结果对运行期账号收回 DELETE；
关联与参与者映射收回 UPDATE、只授出撤销用的那两列。
受众表（决定 8）是例外：它存的是可随时改的选择而不是事实，因此保留 UPDATE 与 DELETE（改选、清空）。

### 8. 问卷受众：存条件不存名册，发布时现算成 `participants`

`survey_audience` 一份问卷一行，存的是**条件**——名单 / 部门（含子孙）/ 标签的交集，至少给一项
（不给条件等于"全租户所有联系人"，一次误发布就会给整个租户发邀请）。发布时（`SurveyPublishService`
固化定义快照的那一刻）才算成名册，写进定义的 `participants[]`。

- **只在需要邀请码时才发**：`policy.access.invitationRequired` 为真才物化；为假时定义里连
  `participants` 这个键都不出现，发布回执的形状因此与本片之前逐字节一致。
  要邀请码却没选人，发布在平台侧就失败（不调网关），错误直说缺的是受众。
- **条目上只有 `ref`＝联系人 id**，姓名、邮箱、手机号一概不发给引擎。一来发布尝试与已发布版本的
  定义快照是不可变的，个人信息写进去就再也删不掉；二来平台自己按联系人地址发邀请，引擎不需要
  知道收件人是谁。客户端写进草稿的 `participants` 在保存时就被丢掉，这个键只有平台能写。
- **按发布者当时的数据范围算**（决定 4）：发布者看不见的联系人不会被邀请。看不见就等于不存在。
  单次上限 2000 人，取到第 2001 个就拒绝，绝不悄悄截断成半批邀请。
  读受众（`find` / `recipients`）与写受众一样要两道判定：通讯录权限，**以及这份问卷本身可不可见**。
  少了后者，任何持通讯录角色的人都能按 surveyId 枚举出"这份问卷邀请了哪个名单 / 部门 / 标签、多少人"。
- **回执回来后在发布收尾的同一事务里登记**（`ContactParticipationService.linkIssued`）：按 `ref`
  逐条写进 `contact_participation`。绝不允许"路由登记了，却没人知道码发给了谁"。
  这里不重判通讯录权限：授权发生在物化受众的那一刻，后台核对用系统身份收尾同一次发布时也必须能登记；
  该方法因此只对通讯录包可见，模块外拿不到这条跳过数据范围判定的入口。版本号与引擎问卷由发布收尾
  直接传下来（`SurveyParticipantSource.Target`）——它刚写完这一版，每个邀请码再查一次已发布版本
  会把每一版的完整定义反序列化一遍，而这一切都在问卷行锁里。
- **登记失败要分清两类**：回执本身不可用（认不出的 `ref`、同一个人来了两条、两人共用一个码）重发拿回的
  是同一份存档回执，结论只会一样，所以判**确定失败**（`publish_failed`），与"回执缺邀请码""策略没落地"
  同一类；其余（数据库不可用之类）才可能是瞬时的，整笔回滚转待核对，下次核对用同一 `requestId`
  拿回同一份回执重来，邀请码不会丢。
- **回执里没有邀请码就判发布失败**（不是待核对）：定义带了几个参与者就必须回来几个码，对不上说明
  引擎里那份问卷不能用，重发只会拿到同一份坏回执。不登记路由、不写版本，引擎里那份按孤儿记录。
- **重新发布：旧映射原样留着，不撤销**。改版再发布是新版本、新 sid、一批全新的邀请码（ADR 0012），
  新映射写在新版本号上，两条唯一索引都不会冲突。所有读取路径（`current` / `forSurvey`）一律按
  当前在线版本过滤，旧映射因此不可能被当成现行的码；旧引擎问卷随后由 `SupersededVersionCloser`
  收口，旧码也就进不去了。留着它是为了"某人在第 N 版拿到过哪个码"这条事实可追溯。
- **邀请码在平台侧只落一处**：`contact_participation.participant_token`，因为投放车道必须凭它发邀请。
  它不进审计资源串、不进日志、不进发布尝试或已发布版本的定义快照；回执里的 `invitations[]`
  只在收尾事务的内存里经过一次。网关按 `requestId` 永久存档回执已经是一条已知遗留（ADR 0016），
  平台不再制造第二处。保留期与映射同寿，撤销（`revoke`）之后行仍在但已失效——见诚实清单。

## 现在还不成立的（诚实清单）

1. 组织同步（`OrgDirectorySyncService`）还没有往 `contact` 里落 `org_member` 联系人，
   `contact.principal_id` 与部门的 `external_ref` 目前只有导入与手工路径会写。
2. `contact.actor_id` 只在停用联系人时用来收回部门范围；平台成员被 access 移除时，
   通讯录这边不会自动停用对应的联系人行（权限已经失效，但联系人还在"在职"状态）。
3. 导入只接受一次性提交的 CSV/JSON 文本（默认上限 8 MiB / 50000 行），没有分片上传、没有对象存储来源。
4. 增量同步、退订与频控、联系人画像与旅程状态机（R18-04 后半、R18-05～R18-07）不在本切片。
5. 邀请码在平台库里没有保留期：`contact_participation` 对运行期账号收回了 DELETE，撤销只写
   `revoked_at`，那一行里已经失效的令牌文本会一直留着。旧引擎问卷收口后这些码进不去任何问卷，
   但"过期凭据不落盘"这件事还没有做，需要一条运维侧的清理策略。
6. 受众读取（决定 8）的问卷可见性判定，**"权限被拒"那一支目前不可达**：现行角色目录里，
   凡带租户级 `manage-members` / `manage-settings` 的角色（`tenant_owner`、`org_admin`、
   `project_manager`）都同时带租户级 `view`，构造不出"有通讯录权限、却对该问卷无 VIEW"的调用者。
   为一条测试往所有租户共享的 `access_role` 里加测试专用角色，比留下这个缺口更糟，所以没加。
   现在覆盖到的是"问卷不存在 / 是别的租户的 / 根本不是问卷"这一支——它确实走到守卫本身
   （去掉 `requireSurvey` 立刻转红），足以挡住重构腐烂。等角色目录能把这两种权限分开，
   再补"权限被拒"那一支的测试。注意这条闸在 HTTP 层看不出差别：控制器把"没有受众"也映射成 404，
   跨租户另有行级安全，所以红只出现在服务层。
7. 登记邀请码时"可能是瞬时的失败"那一支（数据库不可用之类）没有自动化测试：公开 API 上能触到的
   失败都是确定性的，硬造一个替身会和 `ContactSurveyParticipants` 这个 `@Component` 桥接打架。
8. 去重只在名单内。跨名单的"同一个人"要靠 `contact_link` 人工关联，没有自动的实体消解。
9. 没有"合并两行"的撤回路径——因为根本不提供合并；R18-04 的"去重合并可撤回"目前只覆盖到
   "关联可撤销"。

## 验证

`cn.mjy.platform.contacts` 下 89 个用例（先确认 RED：整包不编译），覆盖：
同一 openid 在两个应用/两类身份下不合并；员工与受访者同邮箱仍是两行；关联不合并、幂等、可撤销可重建；
四种去重键各自的库内去重与文件内去重；坏行不终止导入；未知部门只坏一行；
崩溃后续跑不重复建人、重放同一行不重复建人、租约被别人持有时不二次认领；
部门管理员读不到、写不进别的部门；移动部门不泄漏联系人；部门管理员不能把部门移出自己的范围；
撤销范围行后归零而不是提权；离职（access 移除成员）立刻失权；停用员工联系人连带收回范围；
标签按租户隔离；参与者令牌一人一码、不互用、可撤销重发；全部 12 张新表的裸 SQL 跨租户负面测试与
