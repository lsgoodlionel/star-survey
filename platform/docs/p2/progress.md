集成时修复：
- **CRITICAL：飞书事件回调是 CBC 填充预言机**——未签名请求跳过验签却仍用调用方给的 IV 解密，且各种失败返回不同状态与消息，匿名方不知密钥即可逐字节解密并伪造"成员离职"事件。现在任何解密之前先验签（握手也一样），所有取决于请求内容的拒绝统一为同一个 401 与同一段响应体（原因只进服务端日志）。发现于合并后的独立安全审查，修复前未推送。
- 共享 e2e 驱动 `Database` 的容器参数改为可选（此前我的改动弄坏了逻辑与答卷读取两个驱动）；答卷读取 runner 跟随容器前缀。
- 引擎测试栈切换 `TEST_DB` 时重启 web 容器：opcache 按时间戳隔几秒才重新校验，紧接着的请求会用上一种数据库的配置（顺序相关的偶发失败）。

### 缺口 (b)：一份答卷属于哪个邀请码（已完成）

读端点新增可选 `includeRespondent`，每条答卷多回一个 `token`；不传时应答形状与契约本节之前逐字节
一致，也不会多问引擎一次问卷属性。只要身份时 `fields` 可传空数组，不必多请求一列无关作答。

匿名问卷永不给令牌。引擎只在非匿名时给答卷表建 `token` 列（`SurveyActivator.php:253`），但"列里
有值"不能当作可以发的依据：问卷可以先以非匿名激活、写满列与值，之后再改成匿名。所以按问卷**当前**
的 `anonymized` 判定，判定不出来就不给。端到端里这个状态是直接改库造的——引擎自己挡住了 RPC 这条路
（激活后 `set_survey_properties` 会剔除 `anonymized`，`remotecontrol_handle.php:506`），该状态只能
由直接改库／插件／运维造出来，而闸门的意义正是不信任列里有值。

`token` 不再能当普通列请求（400）。`fields` 的正则本来就匹配 `token`，直接写进去就绕过了匿名判定
——这是改动前真实存在的洞。

平台侧：`HttpResponseAnswerSource` 实现新的窄接口 `RespondentSource`；
`GatewayRespondentIdentityResolver` 据此实现 `RespondentIdentityResolver`，网关配置好时才注册
（`@Conditional`），催答对账自动生效。**令牌不落库**，每轮现读现用，平台库里不多一份可直接进入问卷
的凭据。

两处刻意钉死的行为：
- **读不到 ≠ 没答完**。网关不可达或拒绝时返回空映射，这一轮认不出任何人，不登记、不前进游标、
  下轮重来。若把读取失败当成"没有完成记录"，催答会朝一批其实已经答完的人发提醒。
- `RespondentIdentityResolver` 改为**按批**问。对账一页 200 份答卷、读端点一次收 500 个答卷号，
  逐条调用会把一次对账放大成两百次 HTTP。该接口主代码里本无实现，改动面封闭。

测试：网关 678 通过（676 → 678）；平台 996 通过、0 失败 0 错误（986 → 996）；
`run-response-read.sh` 双库均过，七项令牌断言全绿，其中两条是要害——读到的令牌正是发布回执里的
邀请码（(a) 与 (b) 在真实引擎上接上），以及改为匿名后引擎表里其实还存着令牌却返回 null。

遗留：`includeRespondent` 每次读取多一次 `get_survey_properties`，没有缓存。平台仍不在定义里发
`participants`，所以"联系人 → 邀请码"的上游（把名单物化成带 `ref` 的参与者）仍属投放车道待做。

R02-17 与 R02-18 因此**一行插件校验代码都没改**；四类下来插件侧只动过一次。
