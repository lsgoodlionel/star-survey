## Hosted Python 信任链

工作流的两个 job 都由固定完整 commit 的 `actions/setup-python` 提供 Python 3.11。进入 wrapper 前，工作流对 `/opt/hostedtoolcache/Python`、版本父目录、`$pythonLocation`、`bin` 和最终 `python3.11` 常规文件执行 `chmod go-w`；随后立即通过唯一受控入口 `scripts/agent-harness --python --version` 验证实际选择的是 Python 3.11。

wrapper 不直接信任 `pythonLocation`。hosted 候选仅在 `AGENT_HARNESS_CI=1` 下启用，并严格限定为 `/opt/hostedtoolcache/Python/3.11.<纯数字 patch>/x64/bin/python`。shell 阶段逐级检查可信根、父目录 owner/mode、symlink chain、最终 regular executable，并记录 device、inode、owner 和 mode 指纹；隔离 Python 阶段重新解析同一链、比对指纹和 `sys.executable`，同时绑定最终 `python3.11` basename 与实际 minor 版本。空格、Tab、字面换行、可写目标、逃逸和身份变化均已有回归覆盖。

工作流的 hardening 是 GitHub hosted runner 的环境适配，没有放宽 wrapper 的通用信任策略。即使 hardening 缺失或布局变化，wrapper 也会拒绝 hosted 候选并走受控 fallback/typed failure，而不会静默执行未校验解释器。

## 工具身份指纹

提交 `1d5a4a2d861b6a83cd9d9a1b85e45db18b10c413` 将受控工具的 entry、target 和 symlink-chain identity 从 `(device, inode, uid, mode)` 扩展为 `(device, inode, uid, mode, size, ctime_ns)`。绑定后若工具内容被替换、原地改写或元数据发生变化，后续 `_trusted_tool_directory` 复验会 fail closed；root-owned 或当前用户拥有且父链不可被组/其他用户写入的既有边界保持不变。

该改动解决了 CI 中工具路径未变但可执行内容发生变化时旧四元组识别能力不足的问题，且没有以 path/name 代替真实文件身份。测试侧对自治循环的 command builder 进行显式 patch，使测试不再受 import 时宿主工具绑定结果影响，提升了不同 runner 间的确定性。
