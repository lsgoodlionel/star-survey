## 1. 决策摘要

当前阶段从“继续扩展后端能力”切换为“将已经完成的后端能力完整产品化，并形成可上线、可安装、可升级、可卸载的单机生产版本”。

本阶段冻结新的后端业务范围，只允许三类后端修改：

1. 前端接入现有能力所必需的查询、聚合或契约补充。
2. 全量核查报告确认的安全、一致性和生产阻断修复。
3. Docker Compose 单机生产、安装升级和 GitHub Releases 所必需的运行能力。

剩余未完成后端业务包不与本阶段并行扩张。在本阶段通过生产验收后，再依据 305 条需求矩阵安排后续开发。

采用“纵向产品化交付 + 生产基线并行门禁”：每个产品波次必须同时具备页面、真实接口、用户流程、生产 Compose 验证和需求证据，不能再把 Controller、测试或文档存在单独视为产品完成。

## 2. 目标与非目标

### 2.1 本阶段目标

1. 为已有后端能力建立统一、中文、可发现的管理端入口。
2. 按真实用户任务打通发布、预览、投放、答卷、导出、模板、品牌和通讯录闭环。
3. 完成编辑器 Phase C 和首批高级题型的可视化配置。
4. 提供可上线的单机 Docker Compose 生产方案。
5. 提供 Ubuntu 22.04/24.04、AMD64/ARM64 的一键安装、升级、备份、恢复和卸载工具。
6. 使用 GitHub Actions 构建多架构镜像和版本化安装包，并通过 GitHub Releases 发布候选版与稳定版。
7. 修复生产前必须关闭的安全缺口，建立安装、升级、回滚、备份恢复和最小业务探针证据。
8. 统一需求、蓝图、实施计划、仓库进度和 Obsidian 记录的状态口径。

### 2.2 非目标

- 不在本阶段新增统计、AI、支付、预约、签署、投票、360、体验管理等尚未完成的后端业务包。
- 不重写 LimeSurvey 原生后台，也不把它作为业务用户入口。
- 不在首个生产版本承诺 Kubernetes、高可用、多节点数据库或跨区域灾备。
- 不把单机生产方案描述为多副本或云原生方案。
- 不把本地快速预览描述为真实 LimeSurvey 运行时预览。
- 不以空页面、静态假数据或禁用菜单冒充产品化完成。

## 3. 完成口径

每项能力必须同时满足六层证据才能标记“产品完成”：

1. **需求层**：需求编号、角色、前置条件、正常流、失败流和验收断言明确。
2. **后端层**：真实接口、权限、租户隔离、状态机和错误语义可用。
3. **前端层**：导航可发现、业务文案完整、加载/空/错误/无权限状态可操作。
4. **流程层**：真实浏览器串起管理端、平台、网关、数据库和 LimeSurvey。
5. **生产层**：同一流程在 Production Compose 中通过，配置不依赖开发入口或测试数据。
6. **追溯层**：自动化证据、进度文档、需求矩阵、发布版本和 GitHub 记录一致。

“工程切片完成”和“需求 Accepted”继续分别记录。前者用于排期，后者用于产品验收。

## 4. 产品信息架构

### 4.1 一级工作区

管理端扩展为五个一级工作区：

| 工作区 | 面向任务 | 首批页面 |
|---|---|---|
| 工作台 | 恢复工作、处理待办、查看运行摘要 | 最近问卷、待审批、发布异常、快捷入口 |
| 问卷 | 创建、配置、预览和发布问卷 | 资源、模板、编辑、品牌、访问策略、发布与版本 |
| 投放 | 管理受众和触达任务 | 联系人、名单、链接、二维码、批量任务、催答 |
| 数据 | 查看答卷和生成交付物 | 答卷、摘要、字段、导出任务、下载 |
| 管理 | 配置租户及平台运行资源 | 成员、组织连接、套餐、引擎实例、平台模板 |

一级工作区必须使用真实可用路由。未形成纵向闭环的页面不进入正式导航。

### 4.2 问卷内工作流

现有 `SurveyShell` 扩展为：

```text
编辑 | 导入 | 品牌 | 访问规则 | 真实预览 | 发布与版本 | 投放 | 答卷与导出
```

小屏允许分组进入二级菜单，但不能隐藏当前发布状态、草稿版本和未保存状态。

发布成功后的首要操作是“真实预览”“获取答卷链接”“查看答卷”，不再停留在只有版本号的终点页。

### 4.3 引擎入口边界

- 平台管理端是作者、审核者、租户管理员和运营人员的唯一业务入口。
- LimeSurvey `/admin` 只供平台运维使用，不进入业务导航。
- 生产反向代理把引擎后台固定暴露为 `/engine-admin/*`，并通过独立运维身份认证限制访问。
- LimeSurvey 作答运行时继续承担真实预览和正式答卷。

## 5. 产品化波次

### Wave 0：需求基线与生产骨架

交付：

- 新版前后端需求清单、产品蓝图、总体升级方案和分计划索引。
- Production Compose、反向代理、持久卷、环境模板和健康检查。
- `surveyctl` 生命周期工具骨架。
- 多架构镜像和 GitHub Release 流水线骨架。
- 生产安全阻断清单和修复顺序。

验收：生产配置能够在无开发入口、无测试令牌、无宿主机数据库端口的条件下启动并通过健康检查。

### Wave 1：发布后闭环

交付：

- 发布页显示真实运行状态、公开答卷地址和二维码。
- “真实预览”使用隔离的 LimeSurvey 运行时，不写入正式答卷。
- 发布页显示答卷数量、回收状态和数据/导出入口。
- 公开链接、短链和嵌入信息进入问卷上下文。

验收：作者从已发布问卷进入真实预览、获取答卷链接、完成一份真实作答，并在数据页看到该答卷后生成导出。

### Wave 2：模板与品牌闭环

交付：

- 租户模板和平台模板浏览、筛选、详情、复制和审批。
- 品牌主色、页面标题、页脚、Logo/素材选择和多语言配置。
- 品牌配置进入隔离真实预览，并随发布版本固定。

验收：从模板创建问卷，配置品牌，真实预览，发布并完成品牌化作答。

### Wave 3：数据产品化

交付：

- 答卷列表、复合筛选、字段选择、摘要和权限提示。
- 导出任务创建、进度、取消、失败重试、下载和过期状态。
- CSV、XLSX、SAV、DOCX 和附件包只展示真实支持的格式。

验收：跨版本答卷查询无漏重；无明细权限角色只能看摘要；下载前再次授权。

### Wave 4：通讯录与投放

交付：

- 联系人、部门、标签、名单和导入任务。
- 问卷受众、投放链接、二维码、批量任务、回执、催答和退订状态。
- 未配置真实短信/邮件供应商时显示明确的通道不可用状态，不使用成功假数据。

验收：从名单选择受众，创建投放任务，查看逐收件人状态，并证明完成者不再收到催答。

### Wave 5：编辑器 Phase C 与高级题型

交付：

- `820–1179px` 大纲 + 编辑区 + 属性检查器布局。
- 题型面板、中文题型名称、保存时间、版本和冲突状态。
- 专项键盘、读屏和触摸替代路径。
- 首批可视化高级题型：折叠栏目、多级下拉、轮播图。

验收：三种高级题型能够配置、保存、真实预览、发布、作答和回读；未知字段继续无损往返。

### Wave 6：运营后台与生产验收

交付：

- 租户、套餐、成员、组织连接、引擎实例和平台模板管理。
- 生产安全修复、容量基线、备份恢复和升级回滚演练。
- 安装、运维、升级、故障排查和卸载文档。

验收：一台干净 Ubuntu 服务器可以安装稳定版、完成最小业务旅程、升级到下一候选版、验证数据、回滚或卸载。

## 6. 单机生产拓扑

```text
Internet
   |
80/443
   |
Reverse Proxy
   |-- /                 -> Admin Web
   |-- /v1               -> Platform Service
   |-- /survey/*         -> LimeSurvey Runtime
   |-- /engine-admin/*   -> LimeSurvey Admin（运维访问策略）
   |
Internal Docker Network
   |-- Publish Gateway
   |-- PostgreSQL
   |-- MariaDB
   |-- Backup Job
```

### 6.1 服务边界

| 服务 | 责任 | 公网暴露 |
|---|---|---|
| Reverse Proxy | TLS、路由、安全头、请求限制、运维入口限制 | 80/443 |
| Admin Web | 静态前端制品 | 否，代理访问 |
| Platform Service | 业务 API、身份、权限、状态机 | 否，代理 `/v1` |
| Publish Gateway | 平台到引擎的受控适配 | 否 |
| LimeSurvey | 真实作答和运维后台 | 否，代理指定路径 |
| PostgreSQL | 平台数据 | 否 |
| MariaDB | LimeSurvey 数据 | 否 |
| Backup Job | 一致性备份、校验和和保留策略 | 否 |

### 6.2 数据持久化

必须独立持久化：

- PostgreSQL 数据。
- MariaDB 数据。
- LimeSurvey 上传文件和插件运行数据。
- 平台资产、导出和临时预览制品。
- 反向代理证书与 ACME 状态。
- 应用配置、版本清单和迁移记录。
- 加密备份。

普通卸载不得删除上述数据。彻底卸载使用单独危险参数并二次确认。

### 6.3 生产配置

- 公网仅监听 `80/443`。
- 容器内部服务使用独立网络，数据库不发布宿主机端口。
- 所有镜像固定语义版本和 digest，不引用浮动 `latest`。
- 密钥在安装时生成或由运维注入，不进入镜像、Git、Release 包或日志。
- `force_ssl=on`、安全 Cookie、可信代理头和 `ssl_disable_alert=false` 只在真实 HTTPS 验证通过后启用。
- 生产 bundle 不包含 `/dev/token`、E2E 模式或固定演示账户。

## 7. Ubuntu 生命周期工具

### 7.1 支持矩阵

首个生产版本同时支持：

- Ubuntu 22.04 LTS AMD64
- Ubuntu 22.04 LTS ARM64
- Ubuntu 24.04 LTS AMD64
- Ubuntu 24.04 LTS ARM64

目标主机必须使用 systemd 和 Docker Engine + Compose plugin。安装器可安装缺失依赖，但必须显示将要使用的软件源和版本，不静默修改非 Ubuntu 系统。

### 7.2 `surveyctl`

统一命令：

```text
surveyctl install [--version X.Y.Z] [--offline PACKAGE]
surveyctl upgrade --version X.Y.Z
surveyctl rollback [--version X.Y.Z]
surveyctl backup [--output PATH]
surveyctl restore BACKUP
surveyctl status
surveyctl doctor
surveyctl logs [SERVICE]
surveyctl uninstall [--purge-data]
```

行为约束：

- `install` 检查系统、架构、Docker、Compose、端口、磁盘、时间同步和 DNS，生成配置并启动服务。
- `upgrade` 必须先下载并校验目标版本、执行兼容预检和升级前备份。
- `rollback` 只对 Release 元数据声明可回滚的版本开放。
- `backup` 记录应用版本、数据库 schema、镜像 digest、文件清单和校验和，并加密输出。
- `restore` 拒绝不兼容版本、损坏校验和或缺少密钥的备份。
- `doctor` 输出脱敏诊断，不打印密码、Token、Cookie、完整证书私钥或环境文件。
- `uninstall` 默认保留数据；`--purge-data` 必须交互确认并支持非交互显式确认参数。

### 7.3 升级事务

升级顺序固定为：

1. 验证目标 Release、架构、校验和及兼容范围。
2. 创建升级前备份并验证可读取。
3. 拉取或导入目标镜像。
4. 运行数据库和文件迁移预检。
5. 停止写入并切换服务。
6. 执行迁移。
7. 启动并运行健康检查和最小业务探针。
8. 成功后写入当前版本；失败则按 Release 回滚策略恢复。

数据库迁移不可逆时，Release 元数据必须明确声明 `rollback: restore-only`，回滚只能恢复升级前备份，不能伪装成镜像降级即可完成。

## 8. GitHub Releases 与多架构制品

### 8.1 版本规则

- `vX.Y.Z-rc.N`：候选版本，只进入候选通道。
- `vX.Y.Z`：稳定版本。
- Patch：兼容修复，不改变数据模型契约。
- Minor：新增向后兼容产品能力，可包含可回滚迁移。
- Major：允许明确记录的不兼容升级，必须提供迁移指南。

### 8.2 Release 制品

每个 Release 必须包含：

```text
survey-X.Y.Z-linux-amd64.tar.gz
survey-X.Y.Z-linux-arm64.tar.gz
survey-install-X.Y.Z.sh
survey-X.Y.Z-checksums.txt
survey-X.Y.Z-checksums.txt.sig
survey-X.Y.Z-sbom.spdx.json
survey-X.Y.Z-release.json
RELEASE_NOTES.md
UPGRADE.md
```

离线包包含 Production Compose、环境模板、`surveyctl`、对应架构的 OCI 镜像归档、固定 digest 清单、迁移元数据和运维文档，不包含任何真实密钥。

镜像和校验清单使用 GitHub Actions OIDC 的 keyless Cosign 签名，并生成 GitHub artifact attestation；在线安装和离线安装都必须验证签名与校验和。

`survey-X.Y.Z-release.json` 至少记录：版本、通道、支持的 Ubuntu/架构、镜像及 digest、最低升级来源版本、迁移可逆性、备份 schema 和制品校验和。

### 8.3 CI/CD 门禁

标签流水线依次执行：

1. 仓库质量检查和需求追溯。
2. 前端、平台、网关和插件测试。
3. 真实管理端纵向 E2E。
4. AMD64/ARM64 多架构镜像构建和 manifest 检查。
5. 两种 Ubuntu LTS × 两种架构的安装、升级、卸载测试；AMD64 使用 GitHub 托管 runner，ARM64 使用 GitHub 托管 ARM64 runner。
6. Production Compose 最小业务探针。
7. SBOM、校验和和 Release 元数据生成。
8. 候选版本或稳定版本 Release 发布。

任一必需矩阵分支未运行或跳过时不得发布稳定版。

## 9. 安全与生产阻断

以下问题必须在稳定版前关闭：

1. 附件访问不能依赖 `.htaccess`；反向代理和应用层都要阻止绕过授权的直接下载。
2. RemoteControl 写入路径不能绕过访问策略、服务端计时、限次和校验闸门。
3. 邀请码撤销必须同步到引擎并由真实作答验证立即失效。
4. 管理员认证必须支持生产级身份源；开发 Token 路由不能进入生产 bundle。
5. 服务密钥必须支持轮换、`kid` 和双接受窗口。
6. 生产响应必须有 CSP、HSTS、Frame、Content-Type、Referrer 和 Permissions Policy。
7. Release 必须有 SBOM、校验和和漏洞扫描；严重与高危问题不得发布稳定版。
8. 诊断、CI 制品和安装日志必须通过敏感信息扫描。

## 10. 错误与状态设计

所有新增页面必须有：加载、空状态、无权限、暂时不可用、可重试失败和不可重试失败。

- 服务端 401：清除会话并保留允许恢复的本地编辑上下文。
- 403：显示缺少的业务权限，不泄露不可见资源。
- 404：统一显示资源不存在或不可见。
- 409：保留用户修改并展示冲突解决入口。
- 422：按字段或任务步骤展示业务校验问题。
- 503：展示依赖服务暂时不可用和安全重试入口，不伪造成功。

安装和升级失败必须保留脱敏诊断包。任何失败都不得留下“页面可打开但数据库或迁移未完成”的部分成功状态。

## 11. 测试与验收

### 11.1 产品测试

- React 组件和 API 契约测试。
- Java 平台权限、租户隔离、并发和状态机测试。
- 发布网关和插件真实引擎测试。
- Playwright 桌面、平板和移动纵向流程。
- 键盘、焦点、44px、无横向溢出和专项读屏检查。

### 11.2 生产测试

- Production Compose 无开发配置启动。
- HTTPS、代理头、安全 Cookie 和 `/admin` 访问限制。
- 全新安装、幂等重跑、升级、失败回滚、备份恢复和卸载。
- Ubuntu 22.04/24.04、AMD64/ARM64 矩阵。
- 断电或容器终止后的数据完整性检查。
- 最小业务探针：登录、创建问卷、发布、真实作答、答卷查询和导出。

### 11.3 发布判定

候选版允许记录非阻断缺陷。稳定版必须满足：

- 所有必需测试通过且没有跳过矩阵。
- 严重和高危安全问题为零。
- 安装、升级、回滚或恢复、卸载演练均有证据。
- Release 制品校验和、SBOM、版本元数据和说明完整。
- 本版本涉及的需求、进度和用户可见证据同步完成。

旧 `03-实施与验收计划.md` 的过时目录和未勾选切片不再作为执行清单；它保留为历史计划。新的计划按本设计每个纵向波次独立编写。

## 13. 首个实施计划边界

首个 implementation plan 只覆盖四个可共同验收的部分：

1. 文档和需求基线升级。
2. Production Compose 与 `surveyctl` 骨架。
3. 发布后闭环第一段：真实预览入口、答卷链接、二维码和数据入口。
4. GitHub Releases 双架构流水线骨架。

模板与品牌、数据、通讯录与投放、编辑器与高级题型、运营后台分别编写后续独立计划。各计划必须在前一波形成可运行版本后再开始，避免再次形成大量同时存在但不可见的半成品。

## 14. 成功标准

本阶段完成时必须能够证明：

1. 业务用户无需进入 LimeSurvey `/admin` 即可完成已有后端能力对应的正常流程。
2. 发布后的问卷可以真实预览、投放、作答、查看数据并导出。
3. 模板、品牌和首批高级题型形成配置到作答的可见闭环。
4. 管理端不存在只为占位而显示的一级入口。
5. 一台干净的受支持 Ubuntu 服务器能够一键安装指定版本。
6. 同一服务器能够备份、升级、验证、回滚或恢复，并安全卸载。
7. AMD64 与 ARM64 Release 制品均通过真实安装生命周期测试。
8. GitHub Release 能追溯到需求、提交、测试、镜像 digest、SBOM 和升级说明。
9. 生产安全阻断全部关闭，没有把单机方案冒称为高可用方案。
10. 剩余未完成后端需求保持清晰待办，不与本阶段完成状态混淆。
